# AI Explains Lesson Choice — Design Spec

**Source:** item #11 of the 12 high-impact improvements tracked in `[[project_roadmap_vision]]` memory — "IA explica por que escolheu aquela aula." Chosen over the alternative candidate (a progress/evolution dashboard) as the next feature after closing out the original 5-item pedagogical roadmap, because it directly reinforces the product's core marketing promise ("acompanha sua jornada, não só um chatbot") at very low implementation cost.

## Problem

`selectNextTopic()` in `app/api/lesson/generate/route.ts` already decides, every time a lesson is generated, whether today's topic is a **retry** (a topic the student is still learning, taught with a different methodology this time), a **review** (a mastered topic due for spaced-repetition review), or a **new topic** never taught before. The API response already includes `is_retry`, `is_review`, and `methodology` — but nothing on the client reads them (confirmed: no reference to `is_retry`/`is_review`/`methodology` anywhere in `app/aula/AulaClient.tsx`). The reasoning the app already computed is silently thrown away, and the student never learns *why* they're seeing this particular lesson today — undermining the "personal AI teacher with a plan" feeling the product is meant to deliver.

## Goal

Show the student a short, accurate, one-sentence explanation of why today's lesson is what it is, at the start of the lesson — built entirely from the topic-selection logic that already runs today, with no new AI call.

## Non-goals

- **No new AI/LLM call.** The explanation is generated by a pure deterministic function from data `selectNextTopic()` already computes. This is a hard constraint: it must be free, instant, and can never diverge from — or hallucinate about — the real reason the topic was picked.
- **No correlation with `frequentErrors`/`biggestDifficulty`.** Those fields exist on `StudentContext` but have no structured link to the chosen topic today, and building that mapping is a meaningfully separate problem. A future iteration could layer this in; this feature only uses the `isRetry`/`isReview`/`methodology` signal already tied 1:1 to a topic.
- **No change to `selectNextTopic()`'s selection logic itself.** This feature only *surfaces* an existing decision, it doesn't change which topic gets picked or when.
- **No new lesson step or dedicated screen.** The explanation is one line added to the existing `IntroStep`, not a new interruption before the lesson starts.

## Architecture

### `lib/lesson-explanation.ts` (new)

A single pure function:

```typescript
export function explainLessonChoice(params: {
  isRetry: boolean
  isReview: boolean
  methodology: Methodology
  topicLabelPt: string
}): string {
  const { isRetry, isReview, methodology, topicLabelPt } = params
  if (isRetry) {
    return `Você já praticou "${topicLabelPt}" antes — hoje vamos tentar de um jeito diferente (${METHODOLOGY_NAMES_PT[methodology]}) pra ajudar a fixar.`
  }
  if (isReview) {
    return `Faz um tempo que você não pratica "${topicLabelPt}" — hoje é dia de revisão pra manter na memória.`
  }
  return `Hoje é um tópico novo pra você: "${topicLabelPt}".`
}
```

`Methodology` and `METHODOLOGY_NAMES_PT` are imported from `lib/mastery.ts`, exactly as `app/api/lesson/generate/route.ts` already does for its `retryNote` prompt text — this function reuses the same source of truth rather than duplicating methodology names.

Kept in its own file (not added to `lib/mastery.ts` or inlined in the route) because it's a presentation-facing concern — the sentence a student reads — distinct from `lib/mastery.ts`'s scoring/progression calculations, and because it needs to be independently unit-testable without any Supabase/OpenAI mocking.

### `app/api/lesson/generate/route.ts` (modified)

`POST` already computes `isRetry`, `isReview`, `methodology`, and `topic.labelPt` — all in scope at the point the final response is built. Call `explainLessonChoice(...)` and add one field to the existing response's `lesson` object:

```typescript
lesson: {
  title_pt: generatedLesson.title_pt,
  objective_pt: generatedLesson.objective_pt,
  topic_key: topic.key,
  topic_label_pt: topic.labelPt,
  emoji: topic.emoji,
  methodology,
  is_retry: isRetry,
  is_review: isReview,
  choice_explanation_pt: explainLessonChoice({ isRetry, isReview, methodology, topicLabelPt: topic.labelPt }),
},
```

No change to `buildSteps()`, `AiLessonContent`, or any AI prompt — `choice_explanation_pt` is computed after `selectNextTopic()` and attached directly to the top-level API response, sitting alongside the already-present (and already-unused) `is_retry`/`is_review`/`methodology` fields.

### `app/aula/AulaClient.tsx` (modified)

The client already receives the `lesson` object from `/api/lesson/generate`'s response and threads `title_pt`/`objective_pt` etc. into the `GeneratedLesson` shape consumed by `LessonEngine`. `choice_explanation_pt` needs the same treatment: capture it from the generate response and pass it down to `LessonEngine`, which passes it to the `IntroStep` render case as a new prop.

### `types/lesson.ts` (modified)

`IntroStep` gains one optional field:

```typescript
export interface IntroStep {
  id: string
  type: 'intro'
  title_pt: string
  description_pt: string
  choice_explanation_pt?: string
}
```

Optional (not required) because this field comes from the generate API's top-level response, not from `buildSteps()`'s `AiLessonContent`-driven construction — `buildSteps()` builds the `intro` step without knowing `isRetry`/`isReview` (those live in the `POST` handler, one level up). `AulaClient.tsx` attaches `choice_explanation_pt` onto the already-built `intro` step object before handing `steps` to `LessonEngine`, the same way it already assembles the `GeneratedLesson` object client-side from the API response.

### `components/lesson/IntroStep.tsx` (modified)

Render `step.choice_explanation_pt` when present, above the existing title, styled as a small highlighted note (distinct from the "Nesta aula" eyebrow label and the title itself) — e.g. a `💡` icon and small text in a lightly-tinted rounded box, consistent with how other small contextual notes are styled elsewhere in the lesson steps (e.g. `WarmupReviewStep`'s recent-summary note).

## Testing

- `__tests__/lib/lesson-explanation.test.ts` (new): unit tests for `explainLessonChoice` covering all three branches (retry, review, new-topic), asserting the topic label and methodology name are correctly interpolated, and that retry takes priority if somehow both `isRetry` and `isReview` were true (shouldn't happen given `selectNextTopic()`'s mutually-exclusive branches, but the function's own branch order should be deterministic regardless).
- `__tests__/app/api/lesson/generate.test.ts` (modified): assert the response's `lesson.choice_explanation_pt` is present and non-empty, and specifically differs between a retry-path test case and a fresh-topic test case (reusing the existing `isRetry`/`isReview` test fixtures already in this file).
- `__tests__/components/lesson/IntroStep.test.tsx` (new — no test file exists for this component today): render with `choice_explanation_pt` present, assert the text appears; render without it (undefined), assert nothing extra renders and no crash.
- `__tests__/app/aula/AulaClient.test.tsx` (modified): assert `choice_explanation_pt` from a mocked generate response flows into the `intro` step passed to `LessonEngine`.

## Rollout

No database changes — every field this feature reads (`mastery_status`, `next_review_at`, `taught_count`, topic labels) is already read by `selectNextTopic()` today. No feature flag — ships as one plan, ready for the standard subagent-driven-development flow.
